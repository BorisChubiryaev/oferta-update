# genOferta AI

Веб-приложение для объединения изменений в «Публичную оферту о присоединении к услуге
«Удобный доступ»» (Приложение № 7 к Альбому форм). Развитие модуля OfferMerge из
[app4docs](https://github.com/BorisChubiryaev/app4docs) — с тем же движком, но с ИИ там,
где формальных правил не хватает.

## Идея: ИИ предлагает, алгоритм исполняет

В исходном OfferMerge всё делают правила. Формулировки в нормативных документах устойчивы,
и правила разбирают большую их часть — быстро, бесплатно и воспроизводимо. Но устойчивы они
не абсолютно: одну и ту же правку пишут то «Пункт 4.8 изложить в следующей редакции», то
«изложить п. 4.8 в новой редакции», то через таблицу под инструкцией. Каждая новая
формулировка — это новое правило, и так до бесконечности.

Соблазн — отдать разбор модели целиком. Здесь этого нет, и вот почему: **текст договора
никогда не проходит через модель**. Модель читает инструкцию и отвечает *координатами*:
какая операция, к какому пункту, какой фрагмент инструкции является новой редакцией. Сам
текст Оферты меняет тот же детерминированный движок, что и раньше, — побайтово, по
проверенным координатам.

```
Документы «Изменения»
        │
        ▼
1. Детерминированный разбор          ← правила; быстро, бесплатно, воспроизводимо
        │
        ├── разобрано уверенно ──────────────────────────────┐
        │                                                    │
        └── не разобрано / низкая уверенность                │
                    │                                        │
                    ▼                                        │
2.          Запрос к модели                                  │
            (инструкция + карта структуры Оферты)            │
                    │                                        │
                    ▼                                        │
3.   Проверка схемой  →  Сухой прогон по реальной Оферте      │
     (форма операции)     (цель, якорь и текст существуют?)  │
                    │                                        │
                    ▼                                        ▼
4.        Экран проверки: каждая правка помечена источником
                    │
                    ▼
5.        Движок правит документ (OOXML, побайтово)
                    │
                    ▼
     Оферта с выделенными правками + перечень изменений
```

### Что делает результат проверяемым

| Заслон | Что ловит |
|---|---|
| **Промпт** | модели прямо запрещено сочинять и редактировать юридический текст; `payload` — дословная копия фрагмента инструкции |
| **Схема** (`src/ai/validate.ts`) | операции без якоря, без текста правки, с выдуманным типом, с заменой текста на самоё себя |
| **Сухой прогон** (`dryRun` в `src/ai/hybrid.ts`) | ссылку на несуществующий пункт, якорь, которого нет в тексте, сноску за пределами нумерации. Это тот же код, что потом реально правит документ, — если он говорит «не найдено», при сборке тоже не найдёт |
| **Пометка источника** | оператор видит, откуда пришла каждая правка, и где алгоритм с моделью разошлись |
| **Ничего не теряется** | нераспознанная правка не исчезает: она попадает в список как «вручную» и остаётся на глазах у оператора |

Ни одна операция от модели не попадает в документ, не пройдя все четыре.

### Пометки источника на экране проверки

| Пометка | Что значит |
|---|---|
| `алгоритм` | разобрано формальным правилом, модель не привлекалась |
| `алгоритм + ИИ` | оба источника прочитали инструкцию одинаково — наивысшая надёжность |
| `ИИ` | правило не справилось; операцию предложила модель и прошла все проверки |
| `расхождение` | алгоритм и модель прочитали по-разному. Выбор оставлен человеку: тихо предпочесть любую из версий значило бы спрятать разногласие, которое как раз и указывает на сложное место |
| `вручную` | не справились ни правила, ни модель — правку нужно внести в Word самостоятельно |

## Что где лежит

```
src/
├── engine/        Детерминированный движок (перенесён из app4docs без изменений
│                  семантики). Правит OOXML напрямую: пункты, сноски, таблицы,
│                  нумерация, режим рецензирования Word.
│   └── offer-digest.ts   Новое: компактная «карта» структуры Оферты для модели
├── ai/
│   ├── openrouter.ts     Клиент OpenRouter. server-only: ключ не попадает в браузер
│   ├── json.ts           Разбор JSON из ответа модели (терпим к обёрткам ```json)
│   ├── prompts.ts        Промпты и контракт «модель не пишет юридический текст»
│   ├── validate.ts       Проверка ответа модели схемой
│   └── hybrid.ts         Оркестровка: правила → ИИ → проверка → пометка источника
├── app/
│   ├── page.tsx          Интерфейс: загрузка → проверка → сборка
│   └── api/ai/           Серверные маршруты (единственное место, где живёт ключ)
└── components/
```

Движок в `src/engine/` — рабочий код из app4docs. В нём изменено ровно одно:
`offline.ts` дополнительно отдаёт связь «инструкция → что из неё получилось»
(`analyzeChangeDoc`), без которой нельзя доспросить модель ровно про то, что не
разобралось. Прежняя функция `parseInstructionsOffline` осталась тонкой обёрткой, так что
алгоритмический режим работает в точности как раньше.

## Запуск

```bash
npm install
cp .env.example .env.local     # и вписать свой ключ OpenRouter
npm run dev                    # http://localhost:3000
```

Без ключа приложение работает — в алгоритмическом режиме, честно сообщая об этом на
экране. Это не деградация, а прежнее поведение OfferMerge.

## Развёртывание на Vercel

1. [vercel.com/new](https://vercel.com/new) → Import Git Repository → `BorisChubiryaev/oferta-update`.
   Framework определится как Next.js автоматически; Build Command и Output Directory
   менять не нужно.
2. Settings → Environment Variables:

   | Переменная | Значение |
   |---|---|
   | `OPENROUTER_API_KEY` | ключ OpenRouter (**обязательно**) |
   | `OPENROUTER_MODEL` | `inclusionai/ling-3.0-flash-vl:free` (необязательно) |
   | `OPENROUTER_SITE_URL` | адрес развёрнутого приложения (необязательно) |
   | `OPENROUTER_SITE_NAME` | `genOferta AI` (необязательно) |
   | `OPENROUTER_JSON_MODE` | `off`, чтобы никогда не запрашивать режим JSON (необязательно) |

3. Deploy.

Продакшн-веткой Vercel считает ветку по умолчанию в GitHub. Сейчас это
`claude/offermerge-ai-hybrid-uj1qwe` — она и развернётся. Если ветка по умолчанию
сменится на `main`, в Vercel нужно будет либо переключить Production Branch
(Settings → Git), либо влить ветку в `main`.

Маршрут `/api/ai/parse` объявлен с `maxDuration = 60`: бесплатная модель отвечает
небыстро, а дефолтных 10 секунд на Hobby-плане не хватает.

### После первого деплоя

На экране «Режим разбора» нажмите **«Проверить ключ у OpenRouter»**. Проверка мгновенная и
не тратит токены: спрашивается `/api/v1/key`, а не модель. То же самое из консоли:

```bash
curl https://<ваш-домен>.vercel.app/api/ai/health?probe=1
```

Ответ называет причину прямо. Возможные исходы:

| Что показано | Что это значит |
|---|---|
| `✅ Ключ принят OpenRouter` | всё настроено, можно работать |
| `не похож на ключ OpenRouter: они начинаются с «sk-or-v1-»` | в переменной ключ другого сервиса. Ключи OpenRouter выглядят как `sk-or-v1-…`; строка вида `sk-` + шестнадцатеричные символы — не отсюда |
| `в OPENROUTER_API_KEY лежит не ключ, а похоже на название модели` | значения переменных перепутаны местами |
| `OpenRouter не принял ключ (401)` | форма верна, но ключ отозван, удалён или скопирован не полностью |
| `OpenRouter отклонил запрос (400)` с упоминанием провайдера | дело в связке «модель + провайдер», а не в настройке — см. ниже |
| `OPENROUTER_API_KEY не задан` | переменная не подхватилась — в Vercel они применяются со следующей сборки, нужен **Redeploy** |

Пробел или перевод строки, приехавшие вместе с ключом при копировании, обрезаются
автоматически: это самая частая причина отказа, и перевыпускать из-за неё ключ не нужно.

Затем прогоните одну правку через интерфейс с включённым ИИ. Это первое обращение к
`inclusionai/ling-3.0-flash-vl:free` из реального окружения: в разработке модель была
недоступна (см. «Ограничения»), и держать формат JSON она может хуже, чем платные. Если
окажется так — код менять не нужно, модель задаётся переменной `OPENROUTER_MODEL`.

### О ключе

Ключ читается только серверным кодом. Модуль `src/ai/openrouter.ts` помечен `server-only` —
попытка импортировать его из браузерного компонента ломает сборку, а не утекает в бандл.
Переменная намеренно называется без префикса `NEXT_PUBLIC_`: с ним Next вшил бы значение в
JavaScript, который отдаётся каждому посетителю.

`npm run check:bundle` проверяет собранный бандл на наличие ключа, прямых обращений к
OpenRouter и публичных переменных с секретами — на случай, если защиту обойдут
переименованием.

## Проверка

```bash
npm run verify        # типы + линтер + тесты + сборка + проверка бандла
npm test              # тесты (сеть не нужна: модель подставная)
npm run regress -- ./samples   # прогон по реальным документам
```

Тесты `tests/hybrid.test.ts` проверяют не «хорошо ли отвечает модель», а что происходит,
когда она отвечает плохо: выдумка отсекается прогоном, мусор не роняет сборку, падение ИИ
не делает результат беднее алгоритмического.

### Прогон по реальным документам

`npm run regress` кладёт в `samples/` Оферту (имя содержит «Версия») и документы
«Изменения», прогоняет конвейер и печатает, что применилось, а что нет. Каталог `samples/`
намеренно в `.gitignore`: это внутренние нормативные документы, им не место в истории git.

Результат на текущем наборе (Версия 70 + Изменения 71, 73, 76, 83):

```
инструкций разобрано: 10
операций получено:    10
применяется движком:  8
не применяется:       1   ← кандидаты на разбор через ИИ
требует человека:     1   ← кандидаты на разбор через ИИ
```

Эти две строки — и есть то, ради чего сделан гибридный режим:

* **Изменения № 71, правка 2** — «после текста «статус наличия расчета кредитного
  потенциала,» дополнить…». Якорь в Оферте есть, но записан иначе, и дословный поиск его
  не находит.
* **Изменения № 73, правка 2** — замена заголовков столбцов таблицы с объединёнными
  ячейками: правило честно сдаётся и отдаёт правку человеку.

### Режим JSON и провайдеры

OpenRouter — маршрутизатор: запрос уходит к одному из провайдеров (Novita, Together и
другим), и поддержка `response_format: json_object` зависит от связки «модель + провайдер»,
а не от модели как таковой. Часть провайдеров на неподдерживаемый флаг отвечает не
молчаливым игнорированием, а отказом `400 … does not support feature: structured-outputs` —
и тогда запрос не проходит вовсе.

Приложение это обрабатывает само: режим JSON запрашивается, при таком отказе сразу
повторяется без него, и решение запоминается — следующие инструкции идут правильным путём
без лишнего запроса. Список «известных моделей» здесь был бы бесполезен: он устареет к
следующей неделе, а связок «модель + провайдер» слишком много.

Формат ответа на этом флаге и не держится: модель получает требование отвечать JSON в
промпте, разбор терпим к обёрткам (```json, текст вокруг), а схема проверяется отдельно
в `src/ai/validate.ts`.

## Ограничения

* Модель разбирает инструкции **по одной**. Это дороже, чем одним запросом на документ, но
  ошибка в одной инструкции не портит разбор остальных, и сбой ИИ на середине не обесценивает
  уже разобранное.
* Бесплатные модели OpenRouter отвечают с лимитами (429). Клиент повторяет запрос с
  растущей паузой, но при исчерпании лимита разбор откатывается к алгоритмическому и
  честно сообщает об этом.
* `inclusionai/ling-3.0-flash-vl:free` — модель с поддержкой изображений. Сейчас она
  используется только как текстовая. Разбор сканов и PDF — очевидное следующее применение,
  но здесь не реализован.
* **Живых обращений к OpenRouter в разработке не было**: окружение, в котором писался код,
  не выпускает трафик на `openrouter.ai`. Проверено всё остальное — разбор ответов,
  валидация, поведение при выдумке, мусоре и падении ИИ (через подставную модель в тестах).
  Первый реальный запрос нужно прогнать после деплоя, см. «После первого деплоя».
* Документы разбираются и собираются **в браузере**. На сервер уходит только текст
  инструкции и карта структуры Оферты (~1000 токенов), и только когда ИИ включён. Сами
  файлы никуда не загружаются.
